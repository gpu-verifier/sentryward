# Presentation on GitHub

One visual center: the deterministic result. Follow it with the direct diagnostic, then any source explanation. Keep long text left aligned.

Immediately below the result, keep a compact original-material entry: PTX is the analyzed code, `input.json` supplies the configuration, and `output.json` contains saved verifier findings. The expandable analysis-record index groups links by the reader's task: check the finding, model construction, or numerical result. Each available record links to its field's physical line in the original file (`#L…` on GitHub); a JSON pointer alone is not navigation. Verify actual destinations in native preview. Link files relative to `report.md`, or use a verified pinned blob URL for preview, and retain their hashes in Evidence. Link a separately supplied numerical-check artifact as such, without merging its verdict into memory safety.

State why the selected diagnostic matters before showing its coordinates. In a warning-only result, explain the warning's classification and what remains unproved. In a race candidate, locate the access conflict before interpreting its cause. If several records are retained, state how the displayed one was selected; first-in-file is not most severe. Keep exact source anchors in the tool-result part distinct from code excerpts that explain a mechanism.

Select the shortest code excerpt that actually supports the adjacent claim: include the next barrier for peer stores, the branch selector and target table for dispatch, or the wait operand and continuation for release. Do not juxtapose separate phases beneath a same-phase timeline. Use the derivation to compare alternative sites. Shorter is only better when the reader no longer has to guess a missing connection.

For a release problem, keep the complete local chain in one view: the reader's operation and completion, its notification, the allocator's successful wait, and release. Show the missing guarantee at the precise edge; a reader skipping a store does not imply that a collective barrier stops waiting for its other participants. A polling excerpt must include the predicate and retry branch so success-to-release is visible. For a guarded copy, show how the guard and the actual source address refer to the same selected value; displaying only the guard can hide the relationship being explained.

## Report hierarchy

Use two explicit main parts: `1. Verifier result` and, when supported, `2. Code explanation`. `Evidence appendix` supports both parts. The composer numbers subsections; do not put numbering in authored titles.

The first part separates the finding from `Analysis scope`. The second gives the code context a heading, follows the relevant relationships in named subsections, then ends with a headed `Next check` when needed. Use concise, specific titles; put the section's answer in the paragraph below. For example, `Reader paths: output-store bypass` names the local question more clearly than an unheaded paragraph or a generic `Details` section.

Titles, explanations, diagrams and exact code must describe the same relationship at that level. Supporting derivations sit one heading level below the main subsections. Appendix summaries and exact records stay below those; opening a disclosure must not promote its internals to the same level as the report's main parts.

The first view should reveal what was found, the affected operation/object and the condition that changes interpretation. A shape diagram is useful only if it locates the issue; attach dimensions to their axes and connect the named object to the affected access. Do not repeat a diagram's numbers in a paragraph.

For a pipeline, introduce what it computes, the participating roles and relevant intermediate objects before zooming into a guard or instruction. Show where inputs enter and results leave; keep a compute/consumer feedback path if a one-way chain would misrepresent it. A kernel overview and a protocol map answer different questions: label data dependencies in the overview, then use local arrows for what each participant does. Do not mix object transfer, barrier participation and async completion into one unlabeled chain. A compact context map should let a reader point to the stage containing the finding. Follow the object from creation through use to its next handoff, reuse or release; explain why that boundary matters. State when output processing continues after a resource is released, rather than drawing release as kernel completion. Several unrelated local pictures do not establish this larger story. Keep untraced stages outside the map or label their scope explicitly. Kernel size and instruction counts do not establish explanatory coverage.

## Shared language

- Neutral context, blue operations, purple focus. Color is auxiliary; labels and shapes carry meaning. Avoid filling every sentence with a colored box.
- A directed edge needs an explicit meaning: local control flow, data dependence or saved model order. An overlap has no temporal direction. A missing required ordering edge is not a proven executable race.
- A timeline uses participant columns and logical steps downward. Its caption distinguishes a verifier witness from a possible interleaving, neither of which is automatically an observed GPU execution. The matching short code excerpt follows the table directly; participant, branch, iteration and completion conditions follow the code, so the action-to-instruction connection stays visible.
- Prefer that participant view when checked thread guards and local ordering establish a concrete concurrency example. If saved events lack thread bindings, a source-derived possible interleaving may still explain the mechanism; keep its relationship to the saved pair explicit. Do not add a timeline when only an address overlap is established.
- Code is exact, with decisive opcodes/operands in bold and short semantic captions. Known instruction names link to the matching ISA manual; the physical PTX caption opens the original source range. These are different destinations. Keep both when simplifying the page; do not turn a model instruction ID into a source-line link.
- Use the same operation names in diagrams and text. In prose, name the purpose first (for example, output-accumulator handle), then give the register only where a reader needs to match code. An optional short operand guide beside a snippet can connect the key names to exact tokens. Keep names scoped to the checked definition/use; never rename the original code or pretend compiler registers are stable variable names. Registers, predicates, field names and rule IDs use code spans.
- Tables compare the same property across objects. Put the answer and explanations outside the cells. Do not turn an audit ledger into the main story.

## Progressive disclosure

Default view: result, decisive relation, concise supported explanation. Expanded view: the answer's source derivation. Evidence view: diagnostic records, model/run scope and artifact pointers. Keep any condition that changes the answer visible beside it: a configured bypass, a classification-changing assumption or an unresolved event binding is not optional background. Fold the calculation or lookup supporting that condition. The composer groups a derivation’s exact references in one nested disclosure after its explanation, so the proof can be read without interleaved token lists. Those references remain checked and included. Use at most two disclosure levels. A summary names what the reader will learn; expanded content starts with its meaning, not a bare schema dump. This also applies to context: group its evidence by the computation it supports. Explain a reused barrier’s rounds before deriving the participant count or input arithmetic.

Keep the explanation connected: introduce an object's purpose before its address or register name, then follow the same named relation through the diagram and decisive code. Distinguish a partial result stored in shared memory from the final global output; generic “output store” labels can collapse different stages. A short excerpt must retain the predicate, definition or operand needed to check its caption. Put longer setup code with the derivation that uses it; do not append a second generic code-and-reference recap. When sections move, recheck words such as “above”, “next” and “earlier” against the final reading order.

Reread neighboring paragraphs without their headings. Order the explanation by the reader's next concrete check: establish the direct guarantee being sought before investigating an alternative dependency. Explain why that next relation matters; register use, for example, is a data dependency, not automatically an async-completion guarantee. When a barrier is present but a completion relation is missing, show both in the same focused view: what the barrier coordinates and what must additionally finish. Label their different edge meanings. Do not depict missing model order as a proven bad execution. A paragraph should interpret a table or move the reasoning forward, rather than repeat its rows. Start a local view at the operation being investigated, then show the relevant branch and common continuation. Establish any missing binding between saved records and inspected source sites at the start of the source walkthrough; repeat it only where a particular claim or diagram could otherwise mislead. In an expanded derivation, state what the calculation establishes and why it is needed before listing registers or intermediate values.

Preserve all relevant retained diagnostics, original counts, truncation, important rules and source references. Very large execution/equivalence details stay in the original input artifact with exact JSON pointers and hashes. Do not call the report a complete raw-output dump.

## Native review

Read the report on GitHub with disclosures closed and open, in light/dark appearance and a narrow pane. Check the actual path between result, relation, code and evidence. Look for ambiguous labels, unnecessary matrices, paragraphs masquerading as table cells, clipped code, misleading arrows and hierarchy that disappears when expanded. If a reader must scroll before reaching the endpoint of a small overview, shorten labels or arrange parallel roles side by side; do not shrink text until it is illegible.

Scale the explanation to the obstacle: a single blocked data-dependent branch should not require reading the entire kernel, while a reused barrier cannot be explained by its wait opcode alone. A long PTX file is not evidence of a complex report; identify the interacting roles, paths, phases or completion conditions the reader actually needs.

Word counts and diagram counts are not acceptance tests. Read with disclosures closed, then open only the one needed to check a claim. Can the reader identify the outcome and its scope, follow the affected object through the relevant operations, distinguish saved facts from source reasoning, and locate the evidence for a disputed claim? Record the specific misunderstanding and the passage that caused it; do not turn these questions into mandatory report headings or a score based on present elements.

Read as a GPU programmer unfamiliar with this kernel: can each operation name be tied to an object and participant without decoding model IDs? Can the reader move from the pipeline to the focused relation and then its instructions? Does each disclosure answer a named question before listing records? Remove unexplained labels such as “actor 128” from the main story; retain their exact values in the lookup evidence. A computation diagram earns its space only when that connection is visible.
